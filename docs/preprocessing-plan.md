# 전처리 실행 계획 (확정안)

작성일: 2026-10-09 · 근거: [전처리 파이프라인 설계](preprocessing-design.md)

## 0. 확정된 결정

| 항목 | 결정 |
|---|---|
| 뼈대 | **Docling** (MIT). PDF·HTML 모두 Docling 문서 모델(DoclingDocument)로 통일 |
| PDF 백엔드 | docling-parse (MIT). PyMuPDF(AGPL)는 개발용 프로파일링에만 사용 |
| OCR | RapidOCR 영어 모델. 텍스트층이 없는 영역에만 적용 |
| 표 | Docling TableFormer(accurate). 디지털 표와 이미지 표 모두 |
| 범용 VLM (qwen3.5:9B 등) | **사용하지 않음**. 검증에 실패한 블록은 "검토 필요"로 표시하고 대기열로 보냄 |
| PaddleOCR-VL 1.6 | **비교 시험 후보**. 이미지 표 쪽에서 Docling보다 확실히 나을 때만 해당 경로 전용 엔진으로 채택(4장) |
| 실행 환경 | 개발·검증은 클라우드(CPU 4코어). 본 처리는 로컬 또는 GPU 환경에서 같은 코드로 실행 |

## 0.1 실측 근거 (2026-10-09, Docling 2.137, CPU 4코어)

어려운 쪽 유형 8개(쪽당 1장)와 EMA 평가보고서 연속 10쪽으로 측정했습니다.

| 쪽 유형 | 결과 | 시사점 |
|---|---|---|
| EMA PK 표(병합 셀, 디지털) | 병합 셀 복원, 수치·각주 정확 | PyMuPDF 기본 표 추출(값 3중 중복)보다 확실히 나음 |
| FDA 이미지 표(임상시험 목록, 글자 위주) | 셀 글자는 정확. 다만 빈 열 1개 누락, 그룹 행("PK Similarity Study")이 열 제목에 붙음, 줄바꿈된 시험 ID에 공백 삽입("BM12H -NHV- 01-G- 01"). 표 위 문장 1줄 깨짐 | 구조 보정은 후처리(P4)로 |
| FDA 이미지 숫자 표(2쪽, 표 3개, 숫자 셀 95개) | **숫자 값은 95개 모두 정확히 읽음.** 셀 단위로 정확히 일치한 것은 90개(95%). 나머지 5개는 가림 표시 "(b) (4)"가 숫자 셀에 붙거나, 대시(—)가 "一"·빈칸으로 바뀌거나, 가려진 열 제목("Date")이 옆 셀에 섞인 경우 | 숫자 인식은 충분. 셀 오염은 후처리로 대부분 복구 가능 |
| FDA 이미지 쪽의 본문 문장 | 3쪽 중 2쪽에서 문장 1줄씩 깨짐. 그중 1줄은 **심사자 판단 문장**("This reviewer agrees … causality of") | 가장 큰 위험. 같은 줄을 RapidOCR 단독(216dpi)으로 다시 읽으면 정확(신뢰도 0.99, 1.0) → 엔진 한계가 아니라 Docling 연동 문제 |
| FDA 체크박스 표(라벨 심사) | ☒/☐ 상태는 인식. 표 구조는 목록으로 풀림 | 검색 가치가 낮아 이 수준으로 허용 |
| 2009 스캔본(기존 OCR 텍스트층) | 텍스트층을 쓰면 표가 깔끔함. **OCR을 켜면 쓰레기 줄이 추가됨** | 이 경로는 OCR 끔 |
| 디지털 쪽에 OCR 켜기 | 시간 2배(4.9초 → 10.5초), 결과 동일 | OCR은 이미지 쪽에만 |
| 처리량(연속 10쪽, OCR 끔) | 레이아웃만 0.85초/쪽, 표 fast 1.9초/쪽, 표 accurate 3.05초/쪽 | 표 모델은 표가 있는 쪽에만 |

**정리: 핵심은 쪽 단위 경로 판정입니다.** 같은 Docling이라도 설정을 쪽 유형별로 다르게 써야 품질과 속도가 같이 나옵니다.

**검증 방법과 한계:** 이미지 쪽은 원본 쪽을 이미지로 렌더링해 Docling 출력과 셀·줄 단위로 사람이 직접 대조했습니다(자동 지표 없음). 표본은 BMAB1200 BMER의 이미지 쪽 3장(텍스트층 0자, 쪽 전체가 이미지 1장)입니다. 방향을 정하는 근거로는 쓸 수 있지만 품질 보증은 아닙니다. 정량 판단은 P6 정답 세트로 합니다.

## 1. 단계별 계획

### P0. 환경 준비

- 패키지 버전을 고정합니다(docling, docling-parse, rapidocr). 모델 가중치는 미리 받아 `artifacts_path`에 캐시해서, 본 처리는 오프라인으로도 돌 수 있게 합니다.
- **필요한 네트워크 허용:** 모델 파일이 Hugging Face의 CDN으로 리다이렉트됩니다. `huggingface.co`만으로는 부족하고 아래 도메인이 추가로 필요합니다.
  - `cdn-lfs.huggingface.co`
  - `*.hf.co` (실제로 확인된 것은 `us.aws.cdn.hf.co`, `cas-bridge.xethub.hf.co`)
- **완료 기준:** 샘플 PDF 1개가 Docling으로 변환되고, 모델 캐시 경로가 문서화됨.

### P1. 선별 (`ra-prep select`)

- **라벨:** 허가(BLA·EMA 제품번호·DIN)별로 최신 판만 "처리 대상"으로 둡니다. 이전 판은 원문만 보관합니다.
- **중복 허가 평가보고서:** 근사 중복 판정(MinHash 같은 방식)으로 대표 문서에 연결하고, 처리는 대표 문서만 합니다.
- **제외:** 목차 페이지, 직원 명단, 포장 그림 쪽(쪽 단위는 P2에서 판정).
- **산출물:** 처리 대상 목록(문서 ID, 버전 해시, 제외 사유).
- **완료 기준:** 우스테키누맙 기준 FDA 처리 쪽수가 약 50% 줄어든 것을 수치로 확인.

### P2. 쪽 단위 판정 (`ra-prep route`)

- 프로파일 신호(텍스트층 글자 수, 이미지 면적, 표 후보, PDF 생성 프로그램, 텍스트 품질 점수)로 쪽마다 경로를 정합니다.
  - 경로 종류: `TEXT` / `TEXT_TABLE` / `IMAGE_PAGE` / `LEGACY_OCR` / `ARTWORK`, HTML 문서는 `HTML`
- 판정 결과와 근거는 DB의 `page_routes` 테이블에 저장합니다.
- **완료 기준:** 무작위 100쪽을 사람이 확인했을 때 오분류 5% 이하. 특히 HC 가이던스처럼 배경 이미지만 있는 쪽이 `TEXT`로 판정될 것.

### P3. 추출 (`ra-prep extract`)

| 경로 | Docling 설정 |
|---|---|
| `TEXT` | OCR 끔, 표 구조 끔(레이아웃만, CPU 약 0.85초/쪽) |
| `TEXT_TABLE` | OCR 끔, TableFormer accurate(CPU 약 3초/쪽) |
| `IMAGE_PAGE` | OCR 켬(RapidOCR PP-OCRv6, 비트맵 영역), TableFormer accurate. 텍스트 품질 점수가 낮은 줄은 그 영역만 RapidOCR 단독(216dpi)으로 다시 읽어 교체 |
| `LEGACY_OCR` | **기존 텍스트층 사용, OCR 끔**(실측: 재OCR이 잡음 추가). 텍스트 품질 점수가 아주 낮을 때만 예외적으로 강제 OCR |
| `ARTWORK` | OCR 텍스트만 저장. 검색 가중치 낮음 |
| `HTML` | Docling HTML 백엔드 |

- **예상 속도(CPU 4코어, 제품당 선별 후 약 1,500쪽):** TEXT 약 1,050쪽 × 0.85초 + 표·이미지 약 450쪽 × 3~8초 ≈ 40~60분. GPU 환경에서는 수 분~10여 분으로 예상합니다.
- 더 빨라야 하면 `TEXT` 쪽만 docling-parse 직접 추출(레이아웃 모델 생략, 쪽당 0.1초 미만)로 바꿉니다.
- **캐시 키:** `(sha256, 쪽, 엔진 버전)`.

### P4. RA 후처리 (`ra-prep structure`)

- 머리말·꼬리말 제거(반복 비율 기준). 예: "Reference ID: …", "Assessment report EMA/… Page x/y", "Medicinal product no longer authorised".
- FDA 가이던스 초안의 줄 번호를 제거합니다.
- 섹션 트리를 만듭니다. 우선순위는 PDF 책갈피 → 번호 제목("2.2.") → Docling 제목 블록.
- 말한 주체를 태깅합니다.
  - EMA: Discussion/Conclusion 절 → 기관.
  - FDA: 기본은 기관. "The Applicant states/proposed/submitted/claims" 문장 → 신청자.
  - HC 심사 문서: 기관.
  - 라벨: 라벨.
- 가림 처리를 표시합니다(`(b)(4)`, `(b)(6)`, `CCI` → `redacted`). 표 셀에 붙은 가림 표시는 떼어 내고 셀에 `redacted` 표시만 남깁니다(예: "(b) (4) 31" → 31).
- 표 셀을 정규화합니다. 대시 변형("一", "–")은 "—"로 통일하고, 줄바꿈으로 생긴 ID 안 공백은 시험 ID 패턴에 맞춰 붙입니다("BM12H -NHV- 01-G- 01" → "BM12H-NHV-01-G-01").
- 표마다 캡션, 각주, 시험 ID(예: "SB17-3001", NCT 번호)를 연결합니다.

### P5. 검증과 산출물 (`ra-prep qa`)

- 블록마다 기록: 쪽, 좌표, 유형, 섹션 경로, 말한 주체, 엔진(text_layer / ocr / table_model), 신뢰도.
- 문서별 지표: 텍스트 확보율, OCR 평균 신뢰도, 표 구조화 성공률, 숫자 셀 파싱률.
- OCR 잡음 줄 검출: 문자 다양성이 낮고 짧은 토큰이 반복되는 줄(예: "te o e e oe se", "Tfhosyiir ss t y ts")을 찾습니다. 바로 지우지 않고 P3의 재인식으로 교체합니다. 깨진 줄이 심사자 판단 문장일 수 있기 때문입니다. 재인식도 실패하면 `needs_review`로 표시합니다.
- 표 검증 규칙:
  - 행마다 열 수가 맞는지
  - 숫자 셀이 OCR 토큰과 일치하는지
  - 병합 셀이 반복되는지
- 실패한 블록은 `needs_review`로 표시해 대기열로 보내고, 답변 단계에서 "원문 확인 필요"로 노출합니다.
- **산출물:** `data/parsed/<sha256>.json`(DoclingDocument)과 정규화 블록 → 청킹(`metadata-strategy.md`)의 입력.

### P6. 비교 시험 — 본 처리 전 관문

- **정답 세트(30쪽):** EMA PK 표(병합 셀), EMA 일반 본문, FDA 이미지 표(임상시험 목록), **FDA 이미지 숫자 표(검사치·n(%)·PK 결과, 가림 표시 포함)**, **FDA 이미지 쪽 본문**, FDA 체크박스 표, 2009년 스캔본, HC 제품설명서 표, FDA 라벨, HC SBD(HTML). 이미지 쪽은 제품 4개에 고르게 나눕니다.
- **비교 대상**

  | 후보 | 구성 |
  |---|---|
  | A | Docling 표준(위 설정) |
  | B | A + 이미지 표 쪽만 PaddleOCR-VL 1.6 |
  | C | 기준선: PyMuPDF + RapidOCR |

- **지표:** 표 셀 정확도, 숫자 정확 일치율, **이미지 쪽 문장 깨짐 비율(재인식 전/후)**, 체크박스 정확도, 섹션·말한 주체 정확도, 쪽당 시간(CPU / GPU).
- **채택 기준(초안)**
  - 디지털 표 숫자 일치율 99% 이상
  - 이미지 표 95% 이상
  - B는 이미지 표에서 A보다 5%p 이상 좋고 시간이 허용 범위일 때만 채택

### P7. 본 처리와 신규 제품 측정

- 우스테키누맙 5개 프로그램(+ Stelara)을 처리하고 품질 지표 보고서를 만듭니다.
- 마지막으로 BAT2206(holdout)을 적재하고 전처리합니다. 사람이 손댄 시간과 전체 처리 시간을 기록합니다. 이것이 "다른 제품이 들어왔을 때의 속도" 근거가 됩니다.

## 2. 순서와 의존 관계

```
P0 ─▶ P1 ─▶ P2 ─▶ P6(비교 시험) ─▶ P3 ─▶ P4 ─▶ P5 ─▶ P7
                    └ P3·P4 코드는 P6과 함께 개발(정답 세트로 바로 검증)
```

P6을 본 처리 앞에 두는 이유는 엔진 선택이 바뀌면 P3을 다시 돌려야 하기 때문입니다.

## 3. 위험

| 위험 | 대응 |
|---|---|
| 모델 다운로드 차단 | P0에서 도메인 허용. 안 되면 로컬에서 모델을 받아 캐시 폴더를 넘김 |
| CPU 속도 부족(Docling 표 모델) | 경로 분리(TEXT 빠른 경로). 본 처리는 GPU 환경 |
| 이미지 표 구조 오류 | 검증 규칙 + `needs_review`. PaddleOCR-VL은 P6 결과로 판단 |
| 클라우드 데이터 휘발 | 산출물은 로컬·영구 저장소에서 재생성. 코드와 설정만 git에 둠 |

## 4. PaddleOCR-VL 1.6 판단

- **장점:** 표 인식이 강점입니다(OmniDocBench v1.6에서 96.33%, 개발사 발표치). 라이선스는 Apache-2.0으로 상용 가능합니다. 레이아웃 탐지 모델(PP-DocLayoutV3)과 함께 쪽 전체를 파싱합니다.
- **한계**
  - 0.9B짜리 문서 전용 VLM이라 CPU에서는 느립니다. 공식 CPU 속도 수치는 없고, 비공식 모바일 CPU 사례로 쪽당 약 20초입니다. 실사용은 GPU(vLLM 등) 전제입니다.
  - PaddlePaddle 런타임이 추가로 필요합니다.
  - 출력이 Docling 형식과 달라 변환 코드가 필요합니다.
- **결론:** 뼈대로 쓰기보다는 **이미지 표 쪽 전용 엔진 후보**로 P6에서 비교합니다.
  - 대상은 우스테키누맙 기준 약 400쪽으로, 전체의 4% 수준입니다.
  - 범용 VLM을 배제한 결정과 충돌하지 않도록, 문서 전용 모델로만 한정합니다.
