# 청킹·임베딩 전략 (초안)

작성일: 2026-10-11 · 전제: [메타데이터 전략](metadata-strategy.md), 전처리 산출물 `data/parsed/<sha256>.json`([비교 시험](preprocessing-benchmark.md))
임베딩: bge-m3(dense + sparse) · 답변 LLM: gpt-4o-mini

## 1. 무엇을 찾아야 하는가 (데모 질문에서 거꾸로)

| 질문 | 필요한 근거 | 근거의 형태 |
|---|---|---|
| D2. "비교임상(3상)을 했나? 지금 신청하면 필요한가?" | 제품별 시험 목록, 효능 시험 결과·기관 판단 / 가이던스의 비교임상 관련 절(당시 판·현재 판) | 시험 목록 **표 행**, Discussion 절, 가이던스 **번호 절** + 상태·시행일 |
| D3. "Wezlana는 어떤 근거로 인터체인저블? 스위칭 연구가 필요했나?" | FDA 심사의 인터체인저빌리티 절, 스위칭 시험 결과, 라벨 문구 / 2019 최종·2024 초안 가이던스 | 심사 **절**, 결과 **표 행**, 가이던스 **절** |
| D4. "5개 제품 PK 시험 설계 비교" | 제품별 PK 시험의 대상·군·대조약 출처·용량·1차 지표, PK 결과 | 시험 목록 **표 행**, PK 절, PK 결과 표 |

정리하면 검색 단위는 세 가지입니다.
1. **절 단위 서술**: 기관 판단, 설계 설명
2. **표 행**: 시험 하나, 지표 하나
3. **가이던스 절·문항**: 시점과 상태가 붙은 규정

질문이 대부분 "제품별·기관별로 나눠서 비교"이므로, 청크가 제품이나 시험을 섞지 않는 것이 가장 중요합니다.

## 2. 전처리 결과에서 확인한 사실 (SB17 문서 4건)

| 문서 | 본문 블록 | 블록 길이 중앙값 | 100자 미만 블록 | 표 | 표 행 중앙값(최대) |
|---|---|---|---|---|---|
| EMA 평가보고서 | 1,839 | 100자 | 50% | 100 | 12 (43) |
| FDA BMER | 882 | 60자 | 65% | 99 | 9 (43) |
| HC 제품설명서 | 1,133 | 63자 | 62% | 69 | 7 (30) |
| HC SBD(HTML) | 183 | 139자 | 43% | 3 | 5 (12) |

- 블록이 매우 잘게 나뉘어 있습니다(제목, 목록 항목, 한 줄 문장). **블록 그대로 임베딩하면 안 되고, 절 안에서 합쳐야 합니다.**
- 섹션 경로는 깊이 2~5로 안정적으로 잡힙니다(예: `2. Scientific discussion > 2.6. Clinical aspects > 2.6.2. Pharmacokinetics`). 절 경계를 청크 경계로 쓸 수 있습니다.
- 표가 문서당 70~100개입니다. 숫자 질문(D4)의 근거 대부분이 표에 있습니다.

## 3. 청크 설계

### 3.1 서술 청크 (절 단위로 묶기)

- **규칙:** 같은 말단 절(section_path가 같은 범위) 안에서 연속된 본문 블록을 합칩니다. 목표 길이는 약 **400토큰**(영문 약 1,600자)이고, 최대 600토큰입니다.
- **경계:** 절이 바뀌면 무조건 자릅니다. 말한 주체(speaker)가 바뀌어도 자릅니다. 신청자 주장과 기관 판단이 한 청크에 섞이지 않게 하기 위해서입니다.
- **겹침(overlap)은 두지 않습니다.** 대신 절 제목을 청크 앞에 붙이고, 같은 절의 이웃 청크는 부모 청크(3.3)로 함께 가져옵니다.
- 목록은 앞의 도입 문장과 같은 청크에 둡니다("The following issues were addressed: …").
- 표 바로 아래 각주와 약어 설명은 서술 청크가 아니라 그 표에 붙입니다.

### 3.2 표 청크 (두 가지 표현)

| 표현 | 내용 | 쓰임 |
|---|---|---|
| **표 전체 청크** | 캡션 + 머리글 + 전체 행(마크다운) + 각주. 600토큰을 넘으면 머리글을 반복하며 행 묶음으로 나눔 | 비교 질문, 답변 생성 시 원문 제시 |
| **행 청크** | `캡션 / 행 라벨 / 그룹 라벨: 열 머리글=값; …` 형태의 한 줄. 예: `Table 5 Primary PK parameters (PK set) / Cmax (μg/mL) / Mean (SD): CT-P43 (N=80)=5.35 (1.456); EU-approved Stelara (N=81)=4.57 (1.368); …` | 숫자·시험 ID 정밀 검색(sparse가 강함) |

- 행 청크는 **숫자가 있는 표, 그리고 시험 목록 표에만** 만듭니다. 심사자 명단이나 서식 표는 표 전체 청크만 만듭니다.
- 그룹 행("Cmax (μg/mL)", "PK Similarity Study")은 아래 행들의 라벨로 내려 붙입니다. 행 병합 셀의 값도 해당 행마다 채워 넣습니다.
- `needs_review`가 붙은 칸이 있는 표는 청크 메타데이터에 표시합니다. 답변 시 "원문 확인 필요"로 노출합니다.

### 3.3 부모-자식 구조 (작게 찾고 크게 읽기)

- **검색**은 서술 청크(약 400토큰)와 행 청크로 합니다.
- **LLM에 넘길 때**는 부모를 넘깁니다. 서술 청크의 부모는 말단 절 전체(최대 약 2,000토큰), 행 청크의 부모는 표 전체입니다.
- 이유:
  - 작은 청크라야 검색이 정확합니다. 바이오시밀러 문서는 문장이 서로 비슷해서, 큰 청크는 벡터가 비슷해집니다.
  - 기관 판단은 앞뒤 맥락이 있어야 정확히 읽힙니다.

### 3.4 문서 유형별 차이

| 문서 유형 | 청크 | 비고 |
|---|---|---|
| EMA 평가보고서 | 서술(절) + 표 | Discussion/Conclusions 절은 `speaker=regulator`로, 질문이 "기관 판단"이면 우선 |
| FDA BMER·리뷰 | 서술(절) + 표 | OCR 출처 블록은 `source=ocr`. `(b)(4)`는 `redacted` |
| HC SBD(HTML) | 서술(절) + 표. 허가 후 활동표는 **행 1개 = 활동 1건** | 행마다 날짜가 있음(시간 축) |
| EMA 허가 후 절차 | 행 1개 = 절차 1건 | 결정일을 청크 메타데이터로 올림 |
| 라벨·제품설명서 | 라벨 절 단위 | 최신 판만 처리됨. 인터체인저블 문구 절은 D3 근거 |
| 가이던스 | **번호 절·Q&A 문항 1개 = 청크 1개**(길면 문단 단위로 나누되 문항 번호 유지) | `guidance_status`, `effective_from/to`, `guidance_section_id`, 부분 철회 상태를 모든 청크에 |

**임베딩하지 않는 것:**
- 머리말·꼬리말(이미 `furniture`로 표시됨)
- 목차, 서명 페이지, 심사자 명단, 재무 공개(financial disclosure) 절
- 사용설명서 그림 쪽(`ARTWORK`)의 그림 라벨

이 정보는 원문 보관용으로만 남깁니다.

## 4. 임베딩할 텍스트

```
[US | FDA | review | Pyzchiva (SB17, ustekinumab) | <결정일> | 5.3 Human PK > Study SB17-1001 | regulator]
<청크 본문>
```

- 헤더 형식은 [메타데이터 전략](metadata-strategy.md) 6장을 따릅니다. 헤더는 짧게 유지합니다.
- 제품 이름 변형(코드·브랜드·FDA 접미사)은 헤더에 다 넣지 않고 sparse 벡터와 BM25가 맞추게 둡니다.
- 행 청크에는 캡션과 열 머리글이 이미 들어 있으므로, 헤더는 기관·제품·시험 ID만 둡니다.
- 한국어 질문은 bge-m3의 다국어 dense 벡터로 받습니다. 약어와 제품 코드는 질의를 재작성할 때 영어 원형으로 바꿉니다.

## 5. 검색 흐름

1. **필터 먼저:** 제품 비교 질문은 `program_id`별로 따로 검색한 뒤 합칩니다(교차 오염 방지). "당시/현재" 질문은 가이던스의 `effective_from/to`와 `guidance_status`로 거릅니다.
2. **하이브리드 검색:** bge-m3 dense + sparse. 숫자·시험 ID 질문에서는 sparse 가중을 높입니다.
3. **부모 확장 후 생성:** 상위 자식 청크의 부모를 모아 LLM에 넘깁니다. 인용은 문서·쪽·절 단위로 합니다.
4. D4처럼 표를 만들어야 하는 질문은 위 검색 결과에서 정해진 항목(대상, 군, 대조약 출처, 1차 지표…)을 뽑아 캐시합니다(계획의 L3).

## 6. 정하기 전에 시험할 것 (OCR 때와 같은 방식)

청크 크기와 행 청크의 효과는 추측으로 정하지 않고, 검색용 정답 세트로 비교합니다.

- **검색 정답 세트:** D2~D4에서 나오는 질문 15~20개. 각 질문에 "반드시 찾아야 하는 근거 위치"(문서·쪽·절·표 행)를 적습니다. 답변 문장이 아니라 근거 위치만 적어서 작성 부담을 줄입니다.
- **비교 후보**
  | 후보 | 서술 청크 | 행 청크 | 부모 확장 |
  |---|---|---|---|
  | 1 | 블록 그대로 | 없음 | 없음 |
  | 2 | 절 단위 400토큰 | 없음 | 있음 |
  | 3 | 절 단위 400토큰 | 있음 | 있음 |
  | 4 | 절 단위 800토큰 | 있음 | 있음 |
- **지표:** 근거 재현율@10, 제품 교차 오염률(다른 제품 청크가 상위에 섞인 비율), 숫자 질문 정확 근거율
- **예상 규모:** 선별 후 7,952쪽 → 서술 청크 약 1만 개 + 행 청크 수만 개. bge-m3 CPU 임베딩 시간은 첫 실행에서 측정합니다.
