# 파이프라인 운영·오케스트레이션 설계 (초안)

작성일: 2026-10-11 · 관련 문서: [적재 결과](ingestion-report.md), [전처리 실행 계획](preprocessing-plan.md), [청킹·임베딩 전략](chunking-strategy.md), [로컬 실행 안내](local-run.md)

## 0. 요약

| 항목 | 결정(초안) |
|---|---|
| 서비스 목표 | 요청이나 변경 감지에서 출발해 **적재 → 선별 → 전처리(OCR 포함) → 청크 → 임베딩 → 색인 반영**까지 사람 손 없이 이어지게 합니다. 사람이 들어가는 곳은 두 군데입니다(제품 매핑 확인, 검토 필요 블록) |
| 실행 계기 | ① **요청형**: RA 담당자가 새 성분·제품을 요청(일상 업무) ② **감시형**: 이미 등록된 성분의 새 허가, 라벨 개정, 가이던스 개정 |
| 가장 큰 수작업 | 새 성분의 제품 레지스트리(`config/products.yaml`) 작성. 이것을 "자동 초안 + 사람 확인 관문"으로 바꿉니다 |
| 작업 단위 | 문서 1개 = 작업 1개. 쪽 단위로는 나누지 않습니다 |
| 오케스트레이터 | **Apache Airflow 3를 쓸 수 있고, 이 목표에는 적절합니다.** 다만 처리 상태(무엇을 어떤 엔진으로 처리했는지)는 지금처럼 우리 DB가 관리하고, Airflow는 실행·재시도·자원 제한·예약만 맡깁니다 |
| 선행 작업 | 임베딩·색인 단계 CLI화, PostgreSQL + pgvector, 공유 저장소, 레지스트리 DB화, 요청·상태 테이블, 조건부 재수집(7장) |

로컬 단일 실행(`scripts/run_local.py`)은 그대로 둡니다. 개발과 평가에는 계속 이것을 씁니다.

## 1. 데이터 특성 (오케스트레이션 판단 근거)

| 특성 | 실측·현황(우스테키누맙) | 운영 설계에 주는 의미 |
|---|---|---|
| 규모 | 원문 300개 버전 약 537MB, 전체 11,405쪽 → 선별 후 7,952쪽, 청크 약 6천 개(58개 문서) | 성분 하나는 작습니다. 분산 처리가 필요한 규모가 아닙니다. 다만 성분이 늘면 선형으로 커집니다 |
| 성분마다 규모 차이 | 우스테키누맙은 바이오시밀러 4~5개 | 바이오시밀러가 많은 성분은 프로그램 수가 2배 이상일 수 있습니다. 요청 하나가 수십 시간짜리 작업이 됩니다 |
| 처리 비용 | 문서 단위로 무겁습니다. CPU 4코어에서 쪽당 4~5초. 제품 1개에 1.2~2시간, 전체 약 10시간. GPU는 Docling 쪽을 크게 줄이고, OCR(RapidOCR)은 CPU에서 돕니다 | 몇 시간 걸리는 작업이 기본입니다. 진행 상황 표시와 부분 결과 공개가 필요합니다 |
| 원천 갱신 주기 | 목록 메타데이터는 자주 바뀝니다(EMA JSON 하루 2회, Drugs@FDA 평일 매일, Purple Book 월 1회, HC 주간~매일). 심사 문서는 한 번 나오면 그대로입니다. 라벨, 가이던스, EMA 허가 후 절차는 가끔 바뀝니다 | 매일 하는 일은 싼 메타데이터 확인입니다. 무거운 처리는 변경분에만 합니다 |
| 같은 URL 덮어쓰기 | EMA 제품 정보와 허가 후 절차는 같은 URL에 새 판이 올라옵니다 | URL만으로는 변경을 알 수 없습니다. (URL, sha256)로 버전을 관리합니다(구현됨) |
| 결정성 | 전처리에 LLM이 없습니다. 같은 입력과 같은 엔진 버전이면 같은 결과가 나옵니다 | 실패를 여러 번 재시도해도 같은 결과입니다. 재시도는 네트워크 오류에만 의미가 있습니다 |
| 재실행 | 원문은 내용 해시로 저장하고, 전처리는 (sha256, 엔진 버전)이 같으면 건너뜁니다. 후처리만 바뀐 엔진은 `refix`(문서당 1초 미만)를 씁니다. 임베딩은 텍스트 해시로 캐시합니다 | 오케스트레이터가 아니라 **우리 코드가 멱등성을 보장합니다.** 어떤 실행기를 써도 재실행이 안전합니다 |
| 실패 유형 | FDA 봇 차단(403, "apology"), 200 응답에 HTML 차단 페이지, 모델 다운로드 도메인 차단, 개별 문서 실패 | 기관별 동시 요청 제한과 지연 재시도가 필요합니다 |
| 공유 자원 | 대조약 문서와 가이던스는 여러 요청이 함께 씁니다 | 같은 문서는 한 번만 처리해야 합니다(해시로 중복 제거, 처리 중 잠금) |

## 2. 새 성분·제품 요청: 지금 코드에서 일어나는 일

| 요청 | 현재 동작 |
|---|---|
| 제품명(`--product X`) | 레지스트리에 없으면 바로 오류가 납니다("레지스트리에 없는 제품 … config/products.yaml에 추가") |
| 성분명(`--ingredient X`) | 레지스트리에 프로그램이 없어도 세 기관 카탈로그에서 같은 성분의 허가는 찾아 `registrations`에 남깁니다(`unmapped_registration`). 하지만 **문서는 받지 않습니다**(`pipeline.py`의 `continue`) |

결국 새 성분은 사람이 `products.yaml`을 써야 시작됩니다. 이것이 BAT2206 holdout으로 재려는 "신규 제품 추가 수작업"의 핵심입니다.

**성분마다 새로 준비해야 하는 것**

| 구성 | 성분마다 새로? | 비고 |
|---|---|---|
| `products.yaml`: 성분 동의어, 대조약, 프로그램, 기관별 별칭, 식별자, HC 시드 | **예** | 기관 간 이름 불일치(Wezlana/Wezenla), EMA 중복 허가(Eksunbi = SB17)는 사람이 확인했습니다 |
| `guidances.yaml` | 대부분 아니오 | 바이오시밀러 일반 가이던스는 함께 씁니다. 적용 범위 예외(국소작용 제품 등)만 확인합니다 |
| `query_glossary.yaml` | 아니오 | 일반 RA 용어입니다. 새 적응증 용어 정도만 추가합니다 |
| 질의 라우팅(`ra_chunk.query`) | 아니오 | 레지스트리를 읽으므로 등록되면 자동으로 따라옵니다 |
| 전처리·청크 엔진 | 아니오 | 문서 유형 기준이라 성분과 무관합니다 |
| 검색 정답 세트 | 예(없음) | 새 성분에는 정답이 없습니다. QA 지표와 소수의 점검 질문으로 대신합니다 |

## 3. 요청형 흐름 (목표)

### 3.1 단계

| # | 단계 | 자동 / 사람 | 걸리는 시간(참고) | 사용자에게 보이는 것 |
|---|---|---|---|---|
| 1 | 요청 접수: 성분명 또는 제품명, 기관 | 사람(요청) | — | 요청 번호, 상태 "접수" |
| 2 | **카탈로그 탐색**: 세 기관 목록에서 같은 성분 허가를 모두 찾습니다. 문서는 받지 않습니다(`--no-download`) | 자동 | 수 분 | **기관별 허가 현황표(L0)**. 이 시점부터 D1 같은 질문에 답할 수 있습니다 |
| 3 | **매핑 초안 생성**: 허가들을 개발 프로그램 단위로 묶은 초안을 만듭니다 | 자동 | 수 분 | 묶음 초안과 근거 |
| 4 | **매핑 확인(관문)**: 담당자가 초안을 확정하거나 고칩니다. 확정된 프로그램부터 다음 단계로 넘어갑니다 | **사람** | 사람 시간(측정 대상) | 상태 "매핑 확인 대기" |
| 5 | 문서 적재: 확정된 프로그램의 문서 목록 수집, 원문 다운로드 | 자동 | 수십 분 | 기관별 문서 수 |
| 6 | 전처리: 선별 → 쪽 판정 → 추출(OCR 포함) → 후처리 → QA. **우선순위**: 평가보고서·FDA 리뷰·SBD → 라벨·허가 서한 → 나머지 | 자동 | 제품당 CPU 1.2~2시간 | 처리된 문서 수 / 전체 |
| 7 | 청크·임베딩·색인 반영: **문서 하나가 끝날 때마다** 바로 색인에 넣습니다 | 자동 | 문서당 수 초~수십 초 | 상태 "검색 가능(부분)" |
| 8 | 완료 보고: 문서 수, OCR 쪽 비율, `needs_review` 블록 수, `missing_registration` 경고, 문서가 없는 칸 | 자동 | — | 상태 "완료" 또는 "일부 실패" |

### 3.2 매핑 초안을 만드는 단서 (3단계)

- **FDA**
  - 비고유명 접미사(`ustekinumab-xxxx`)와 BLA 번호
  - Purple Book의 대조약 열과 허가 유형(351(k) Biosimilar / Interchangeable)
- **EMA**
  - `biosimilar` 플래그
  - 판매허가권자 이름
- **HC**
  - DPD 브랜드와 회사 이름
- **기관 간 묶기:** 브랜드명이 같은지, 판매허가권자나 개발사 이름이 같은지 봅니다.
- **EMA 중복 허가 후보**(같은 판매허가권자, 다른 브랜드): 평가보고서를 먼저 받아 본문에서 개발 코드를 찾고, 그것을 근거로 제시합니다. 지금까지 Eksunbi, Qoyvolma, Usrenty를 이 방법으로 사람이 확인했습니다.
- 자동으로 묶지 못한 허가는 "미매핑"으로 남깁니다. 담당자가 기존 묶음에 넣거나, 새 프로그램으로 만들거나, 제외합니다.

### 3.3 "없음"과 "아직 처리 안 됨" 구분

처리 도중에도 검색은 열립니다(7단계). 이때 답변 단계는 **프로그램 × 기관 × 문서 유형의 처리 상태**를 함께 봐야 합니다. 그래야 "FDA 리뷰는 아직 처리 중"인 것을 "FDA 리뷰 없음"으로 답하지 않습니다.

이것은 진행 계획의 "자료 없음 처리 테스트"(BAT2206 × HC)와 같은 문제입니다. 상태 값은 세 가지로 나눕니다.
- 공개 문서 없음
- 적재 실패
- 처리 중

### 3.4 요청 상태

```
접수 → 카탈로그 확인 → 매핑 확인 대기 → 처리 중(n/N 문서, 우선 문서 완료 여부)
     → 검색 가능(부분) → 완료 | 일부 실패
```

문서 단위 상태는 `pending → fetched → parsed → indexed`이고, 갈래로 `failed`와 `needs_review`가 있습니다.

### 3.5 겹치는 요청

- 같은 성분을 두 사람이 요청하는 경우, 그리고 대조약 문서와 가이던스를 여러 성분이 함께 쓰는 경우가 있습니다.
- 원문은 내용 해시로, 처리 결과는 (sha256, 엔진 버전)으로 이미 한 번만 저장합니다.
- 남은 것은 **동시에 같은 문서를 처리하지 않게 하는 잠금**입니다. 문서 버전 행에 "처리 중" 표시와 시작 시각을 둡니다.

## 4. 감시형 흐름: 등록된 성분의 변경 감지

| 소스 | 원천 갱신 | 확인 주기(제안) | 감지 대상 | 후속 작업 |
|---|---|---|---|---|
| EMA 의약품 JSON, EPAR 문서 JSON | 하루 2회 | 매일 | 같은 성분의 새 허가, 문서 `last_updated` 변경 | 새 허가 → **3.1의 3단계(매핑 초안)부터**. 문서 변경 → 재수집 |
| Drugs@FDA ZIP | 평일 매일 | 매일 | 새 BLA, 새 ApplicationDocs, 보충 신청 | 위와 같음 |
| Purple Book | 월 1회 | 월 1회 | 인터체인저블 지정, 독점기간 | L0 갱신(문서 처리 없음) |
| HC DPD·NOC, DHPP 심사 문서 | 주간~매일 | 주 1회 | 새 NOC, 새 SBD·RDS, 제품설명서 날짜 | 재수집 |
| 가이던스(FDA 공식 목록, EMA·HC 페이지) | 수시 | 주 1회 | 새 문서, **상태 변화(초안 → 최종, 철회)** | 아래 "버전이 바뀔 때" 참고 |
| ClinicalTrials.gov | 수시 | 월 1회 | 새 시험, 결과 등록 | `trials` 갱신 |
| 같은 URL 덮어쓰는 문서(EMA 제품 정보·허가 후 절차) | 수시 | 주 1회 + 월 1회 전수 | 내용 해시 변경 | 재수집 |

**지금 구현과의 차이:**
- 적재를 다시 돌리면 모든 문서를 다시 내려받아 해시를 비교합니다. `ETag`과 `Last-Modified`는 저장만 하고 조건부 요청에는 쓰지 않습니다.
- 매일 확인하려면 다음 순서로 범위를 좁힙니다.
  1. 목록 메타데이터의 날짜 필드(`last_updated`, `ApplicationDocsDate` 등)로 후보를 좁힙니다.
  2. 조건부 GET(`If-None-Match`, `If-Modified-Since`)을 씁니다.
  3. 그래도 알 수 없는 것은 월 1회 전수 해시 비교로 잡습니다.

**버전이 바뀔 때**

| 바뀐 것 | 처리 |
|---|---|
| 문서 새 판(라벨 개정 등) | 새 판을 전처리하고 색인합니다. 이전 판 청크는 지우지 않고 `valid_to`를 기록해 기본 검색에서 뺍니다. 원문은 보관합니다 |
| 가이던스 상태·시행일만 바뀜 | 원문이 같아도 청크 메타데이터를 갱신합니다. 컨텍스트 헤더에 `status=`가 들어가므로 **헤더가 바뀐 청크는 다시 임베딩합니다**(텍스트 해시 캐시라 바뀐 것만 계산) |
| 전처리 엔진(후처리만) | `refix` → 청크 텍스트가 바뀐 것만 다시 임베딩합니다 |
| 전처리 엔진(추출 단계) | 전체 재처리(약 10시간급). 백필 작업으로 분리하고 낮은 우선순위로 돌립니다 |
| 청커 버전 | 저장된 파싱 결과에서 다시 청크를 만듭니다. 바뀐 텍스트만 임베딩합니다 |
| 임베딩 모델 | 전체 재임베딩입니다. 새 색인을 옆에 만든 뒤 전환합니다(검색 중단 없음) |

## 5. 작업 단위와 자원

- **작업 단위는 문서 1개입니다.**
  - 머리말·꼬리말 판정(반복 비율)과 섹션 트리가 문서 단위 계산입니다.
  - 모델 로딩 비용은 문서 처리 시간(수 분)에 비해 작습니다.
  - 짧은 문서(HTML, 몇 쪽짜리 서한)는 여러 개를 묶어 작업 하나로 돌립니다.
- **자원 제한**
  - 네트워크: 기관별 동시 요청 1~2개. FDA는 봇 차단이 있어 가장 보수적으로 둡니다.
  - 전처리: CPU 워커 1개당 메모리 약 3GB, GPU는 동시에 1~2개.
  - 임베딩: 전처리와 같은 GPU를 나눠 쓰거나 CPU로 돌립니다.
- **우선순위:** 사용자 요청 > 감시 변경분 > 엔진 백필. 요청 안에서는 3.1의 문서 유형 순서를 따릅니다.
- **재시도**
  - 네트워크 오류: 지수 백오프로 재시도합니다.
  - 차단 페이지(200 HTML): 수십 분 뒤 재시도합니다.
  - 전처리 실패: 결정적이라 1회만 재시도하고, 이후 `failed`로 두고 보고합니다(`prep_documents.reason`).

### 6.3 판단

- **R7과 R8은 어느 실행기를 써도 우리 DB가 맡습니다.**
  - 처리 상태와 버전은 이미 `documents`, `document_versions`, `prep_documents`에 있습니다.
  - 서비스 화면도 이 테이블을 읽어야 합니다. 실행기 내부 상태를 화면의 원천으로 쓰지 않습니다.
- 이전 검토에서는 Dagster의 자산 버전 관리(R8)가 잘 맞는다고 봤습니다.
  - 버전 판정을 우리 코드가 이미 하므로 이 이점은 겹칩니다.
  - 요청형 서비스에서는 R1, R4, R5가 더 중요합니다.
- **Airflow 3를 1안으로 둡니다.**
  - pool(기관별·GPU), 우선순위, REST 실행, 동적 매핑, 사람 승인이 모두 기본 기능에 있습니다.
  - 업계에서 가장 흔해 운영 지식을 구하기 쉽습니다.
  - 대신 Docker로 띄우고 PostgreSQL을 함께 둡니다.
- **Prefect는 2안입니다.** 운영 인원이 적고 사내에 Airflow가 없으면 가장 가볍게 같은 요구를 채웁니다.
- **원칙(실행기와 무관):**
  - 작업은 우리 함수나 CLI를 부르는 얇은 껍데기로 둡니다(`run_ingest`, `ra_prep.pipeline.run`, 색인 함수).
  - 작업 사이에는 ID만 넘깁니다(문서 ID, 요청 ID).
  - 실행기를 바꿔도 파이프라인 코드는 바뀌지 않게 합니다.

### 6.4 Airflow DAG 구성(안)

| DAG | 계기 | 작업 |
|---|---|---|
| `ra_request` | 서비스 API(`conf`: 성분 또는 제품, 기관, 요청자) | 대상 해석 → 카탈로그 탐색 → 매핑 초안 → 매핑 확인(관문, 레지스트리에 이미 있으면 건너뜀) → 문서 적재 → 처리할 문서 목록 → `ra_process` 실행 |
| `ra_process` | `ra_request`, 감시 DAG, 수동 | 문서 ID 목록으로 동적 매핑: [전처리 → 청크·임베딩·색인] 작업 그룹을 문서마다 실행 → 완료 보고 |
| `ra_watch_daily` | 매일 | 등록된 성분의 EMA·FDA 목록 갱신 → 변경 비교 → 새 버전은 `ra_process`로, 새 허가는 매핑 확인 요청으로(담당자 알림) |
| `ra_watch_periodic` | 주간·월간 | HC, 가이던스, Purple Book, ClinicalTrials.gov, 같은 URL 문서 해시 확인 |
| `ra_backfill` | 수동 | 엔진·청커·임베딩 모델 버전 변경 시 대상 판정 → `refix` 또는 재처리 → 재색인 |

- pool: `net_ema`, `net_fda`, `net_hc`(각 1~2), `gpu`(1~2), `cpu_prep`(코어·메모리에 맞춰)
- priority_weight: 요청 > 감시 > 백필

## 7. 선행 작업 (도입 순서)

오케스트레이터보다 아래가 먼저입니다. 이것들은 cron 실행에서도 그대로 쓰입니다.

| # | 작업 | 이유 |
|---|---|---|
| 1 | **색인 단계 CLI화**(`ra-index run` 가칭): 파싱 결과 → 청크(V2) → bge-m3 → 벡터 저장소 반영. 건너뛰기 키는 (문서 sha256, 전처리 엔진, 청커 버전, 임베딩 모델). 이전 판 청크에 `valid_to` 기록 | 지금 임베딩은 평가 스크립트 안에서 pickle 캐시로만 돕니다. 파이프라인 단계가 아닙니다 |
| 2 | **저장소**: SQLite → PostgreSQL + pgvector. `data/raw`, `data/parsed`는 공유 저장소(S3 호환 또는 공유 볼륨). DB에는 절대 경로 대신 저장소 키를 저장 | 여러 워커가 동시에 씁니다(`database is locked`). 클라우드 컨테이너 디스크는 사라집니다 |
| 3 | **레지스트리 DB화**: `products.yaml`은 초기값과 내보내기용으로 남김. 매핑 확정 이력(누가, 언제, 근거) 기록 | 요청마다 yaml을 고치고 커밋하는 방식은 서비스가 될 수 없습니다 |
| 4 | **요청·상태 테이블**: `requests`(3.4 상태), 문서 버전별 단계 상태와 처리 중 잠금 | R7, 3.5 |
| 5 | **매핑 초안 생성**(`ra-ingest propose --ingredient X` 가칭): 카탈로그 탐색 결과로 3.2의 초안을 만듦 | 새 성분 수작업을 "확인"으로 줄입니다 |

| 8 | 오케스트레이터 도입(6.4) | 1~7 위에 얇게 얹습니다 |

**진행 현황 (2026-10-11)**

| # | 상태 | 내용 |
|---|---|---|
| 1 | **완료** | `ra-index run / status / search`. 건너뛰기 키는 문서 버전, 전처리 엔진, 청커, 모델, 메타데이터 해시입니다. 이전 색인은 `retired_at`으로 은퇴시킵니다. 같은 텍스트의 벡터는 다시 계산하지 않고 재사용합니다. 검색은 평가 스크립트와 같은 함수를 씁니다(`check_index_parity.py`로 확인) |

남은 작업과 다음 측정:
- 실제 코퍼스(58개 문서)로 색인한 뒤 `check_index_parity.py`가 통과하는지 확인합니다.
- 첫 색인 시간을 잽니다. CPU 기준이며, 평가 캐시를 재사용할 때와 하지 않을 때를 나눕니다.
- 청크가 수만 개를 넘으면 pgvector HNSW 색인을 비교합니다. 근사 검색이라 정확 검색과 결과가 조금 다를 수 있으므로, 재현율을 다시 확인해야 합니다.

## 8. 측정할 것과 열린 질문

**측정**
- **BAT2206(holdout)으로 3.1 전체를 잽니다.** 요청부터 색인 완료까지의 시간, 매핑 확인에 든 사람 시간, 실패 지점. 진행 계획 P7의 "신규 제품 추가 측정"을 이 흐름으로 합니다.
- **두 번째 성분으로 일반화를 확인합니다.** 바이오시밀러 수가 많은 성분이 좋습니다. 매핑 초안이 맞는 비율, 사람이 고친 항목, 처리 시간을 봅니다.

**열린 질문**
- 실행 환경: 사내 서버, 클라우드, GPU 유무. 6.4의 pool 크기와 처리 시간이 여기에 달려 있습니다.
- 매핑 확인을 누가 하는가: 요청자 본인, 아니면 관리자.
- 대조약 문서 범위: 대조약은 문서가 많고 오래됐습니다(Stelara 2009, 스캔본). 새 성분마다 전부 처리할지, 라벨과 핵심 심사 문서만 처리할지 정해야 합니다.
- 감시형에서 새 바이오시밀러가 발견됐을 때: 자동으로 요청을 만들지, 담당자에게 알리기만 할지.
- 동시 사용자 수와 요청 빈도: 실행기 규모와 우선순위 정책을 정하는 데 필요합니다.
