# 라벨 적재 개편 계획: 문서 계열 구분과 구조화 원천 우선

작성일: 2026-10-13 · 상태: 계획(구현 전)

라벨(FDA 처방정보, EU 제품정보, HC 제품설명서)을 어디서, 어떤 형식으로 받아 처리할지 다시 정합니다. 심사 문서·가이던스 적재는 바꾸지 않습니다.

---

## 1. 새 기준 세 가지

| 기준 | 내용 | 적재에 주는 영향 |
|---|---|---|
| **1. 문서 계열 구분** | 라벨 계열은 **"무엇이 승인됐나"**(적응증, 용법, 제형, 경고)입니다. 심사 계열(평가보고서, FDA 리뷰, SBD)은 **"왜 승인됐나"**(바이오시밀러 근거)입니다. 바이오시밀러 라벨은 원 제품 임상 데이터를 옮겨 적으므로 근거가 거의 없습니다 | 라벨은 기관 간 승인 내용 비교용으로 다룹니다. 근거 추출 대상에서 뺍니다 |
| **2. 구조화 원천 우선** | 같은 내용이 XML로 있으면 PDF보다 XML을 씁니다. FDA 라벨은 DailyMed SPL XML로 받을 수 있습니다 | 라벨 계열은 기관별로 "현행판을 어떤 형식으로 받는가"를 정합니다 |
| **3. 기관마다 라벨이 따로 있음** | SmPC(EU), USPI(US), PM(CA)은 서로를 대신하지 못합니다. 적응증 범위, 개정 시점이 다릅니다 | 프로그램 × 기관마다 현행 라벨과 심사 문서가 갖춰졌는지 적재 단계에서 확인합니다 |

## 2. 현재 상태 (2026-10-13, `temp_data/ra_parsed/ra.db`와 파싱 결과로 확인)

| 기관 | 지금 받는 원천 | 적재 | 전처리 | 비고 |
|---|---|---|---|---|
| FDA | Drugs@FDA 라벨 PDF. 보충 신청마다 1판 | 60건 | 최신판 7건, 440쪽 | Docling 경로. 2단 Highlights, 목차 상용구는 정규식으로 제외 |
| EMA | 제품정보 PDF + 수정 추적 DOCX | PDF 8건, DOCX 3건 | PDF 5건, 881쪽 | Annex I(SmPC)~IIIB(포장설명서)가 한 PDF. DOCX는 `not_pdf_or_html`로 건너뜀 |
| HC | DPD 제품 페이지의 PM PDF | 6건 | 5건, 528쪽 | — |

라벨 계열은 **1,849쪽으로 전처리 전체 7,321쪽의 약 25%**입니다.

### 2.1 이번에 파싱 결과에서 확인한 것

1. **라벨에는 바이오시밀러 근거가 없습니다.**
   - 4개 제품 × 3기관의 최신 라벨을 검색했습니다. 개발 코드(SB17 등)와 "comparative"는 0건입니다.
   - "biosimilar"는 "X is biosimilar to Stelara" 같은 정의 문장 수준입니다. Yesintek EU 제품정보의 187건은 회사명(Biosimilar Collaborations Ireland)입니다.
   - 기준 1이 이 코퍼스에서 그대로 성립합니다.
2. **인터체인저블 문구는 지금 어느 라벨에도 없습니다.**
   - FDA 라벨 포함, 처리된 최신 라벨 17건 모두에서 "interchangeab"가 0건입니다.
   - 인터체인저블 지정 사실의 원천은 Purple Book(L0)과 허가 서한입니다.
   - [청킹 전략](chunking-strategy.md) 5장 표의 "인터체인저블 문구 절은 D3 근거"는 고쳐야 합니다.
   - FDA가 라벨 가이던스 개정에서 라벨에 인터체인저블 표기를 넣지 않도록 권고한 것과 맞아 보입니다. 다만 가이던스 원문으로는 확인하지 않았습니다 ⚠️.
3. **최신판 선별 버그: SB17 FDA 라벨의 지난 판이 색인에 들어가 있습니다.**
   - BLA761373의 최신판으로 `761373s004lbl.pdf`(2025-04-30)가 처리됐습니다.
   - 실제 최신판은 두 BLA를 함께 덮는 `761373s006,761425s005lbl.pdf`(2025-11-19)입니다. 이 문서의 `extra.registration_ids`는 `[27, 28]`입니다.
   - 원인: `ra_prep/select.py`가 문서의 주 `registration_id`만 보고 판을 고릅니다.
4. **같은 판을 두 번 처리하고 있습니다.**
   - Stelara의 `125261s173lbl.pdf`와 `761044s021lbl.pdf`는 둘 다 57쪽이고 블록 1,057개가 같습니다.
   - 라벨 유형은 근접 중복 검사(`DEDUP_TYPES`) 대상이 아닙니다.

## 3. 목표 구조

라벨 계열은 기관마다 **현행판 1개(파싱·색인)**와 **판 이력(원문 보관, 요청 시 처리)**을 갖습니다.

| 역할 | FDA | EMA | HC |
|---|---|---|---|
| **현행판 본문** | **DailyMed SPL XML** | 제품정보 PDF(Annex I 위주) | PM PDF. XML PM이 있으면 XML |
| **판 이력** | Drugs@FDA 라벨 PDF(보충 신청 = 승인 시점) | procedural steps(이미 적재) + 수정 추적 DOCX | RDS + PM 날짜 |
| **앞으로의 구조화 원천** | — | ePI(FHIR). 2026년 4분기부터 백신·항암제 위주로 단계 도입, 제출은 자율 | XML PM(2025-07부터 신규 NDS 의무) |

**Drugs@FDA PDF를 버리지 않는 이유**
- DailyMed 판은 허가권자가 올린 판입니다. 승인일과 1:1로 대응하지 않고, 반영이 늦거나 편집 변경만 있는 판도 있습니다.
- 한 제품에 유통사별 SetID가 여러 개입니다(예: Pyzchiva는 Cordavis와 Sandoz).
- 그래서 "언제 승인됐나"의 기준은 Drugs@FDA 판입니다. SPL은 현행 본문을 정확히 파싱하는 데만 씁니다.

## 4. 작업 계획

### 단계 0: 지금 있는 것 바로잡기 (네트워크 불필요)

| # | 작업 | 위치 | 확인 방법 |
|---|---|---|---|
| 0-1 | 최신판을 `extra.registration_ids` 전체 기준으로 계산합니다 | `ra_prep/select.py` | SB17 `s004`가 `superseded_label`로 바뀜. `ra-index run`에서 그 청크가 은퇴(`retired_at`)함 |
| 0-2 | 라벨 동일판 중복을 제거합니다. 판 날짜가 같은 라벨끼리 근접 중복 검사를 해서 하나만 처리합니다 | `ra_prep/select.py` | Stelara `761044s021`이 `near_duplicate`로 빠짐 |
| 0-3 | 문서 계열 필드를 추가합니다. `DOC_TYPE_PROFILE`에 `family`(`label` / `evidence` / `decision` / `guidance` / `other`)를 둡니다 | `ra_ingest/metadata.py` | 단위 시험 |
| 0-4 | 커버리지 표를 추가합니다. `ra-ingest status`에 프로그램 × 기관 × {현행 라벨, 심사 문서}의 유무, 형식, 판 날짜를 보여 줍니다 | `ra_ingest/cli.py` | 빠진 칸이 바로 보임(예: Upstelda처럼 평가보고서가 없는 경우) |
| 0-5 | 문서를 고칩니다. 인터체인저블 근거 원천을 Purple Book과 허가 서한으로 바로잡습니다 | `docs/chunking-strategy.md` | — |

**합격 기준**
- 단위 시험이 통과합니다.
- 검색 평가 23문항에서 라벨 문항(Q11, Q23)은 재현율이 같거나 오르고, 다른 문항은 변화가 없습니다.

### 단계 1: FDA 라벨에 SPL 원천 추가 (`api.fda.gov`, `dailymed.nlm.nih.gov` 허용 필요)

| # | 작업 | 내용 |
|---|---|---|
| 1-1 | 발견 | openFDA `drug/label`에서 `openfda.application_number:"BLA761373"`로 SetID, 판 번호, `effective_time`, 브랜드명, 제조사를 가져옵니다. ⚠️ 생물의약품 BLA가 `openfda` 필드에 매핑되는지 첫 실행에서 확인합니다. 안 되면 DailyMed `spls.json` 이름 검색으로 대신합니다 |
| 1-2 | SetID 고르기 | 한 BLA에 SetID가 여러 개일 수 있습니다(유통사별, 브랜드 없는 이름). 허가권자(`registrations.holder`)와 labeler가 같은 SetID를 대표로 정합니다. 나머지는 `extra.alt_setids`에 기록만 합니다 |
| 1-3 | 받기 | DailyMed `/services/v2/spls/{setid}.xml`로 받아 `raw/fda/<ab>/<sha256>.xml`에 저장합니다. 문서는 `doc_type=label`, `native_doc_type="SPL"`, `extra={setid, spl_version, effective_time, format: "spl_xml"}`로 기록합니다 |
| 1-4 | 판 이력 | `/spls/{setid}/history`로 판 번호를 기록합니다. [운영 설계](pipeline-operations.md)의 감시형 실행에서 매일 SetID 판 번호만 비교하면 라벨 개정을 싸게 감지할 수 있습니다 |
| 1-5 | 현행판 규칙 | 등록마다 SPL과 Drugs@FDA 최신 PDF를 비교합니다. SPL `effective_time`이 Drugs@FDA 최신판 날짜 이상이면 SPL을 처리하고, PDF는 `structured_source` 사유로 건너뜁니다. 아니면(DailyMed 반영 지연) PDF를 처리하고 경고 이벤트를 남깁니다 |
| 1-6 | 전처리 | `ra_prep/spl.py`를 만듭니다. `html.py`와 같은 블록 스키마를 씁니다. `<section>`의 제목과 LOINC 코드는 절 머리글과 `section_path`, `<table>`은 행·열 병합을 유지한 셀 격자, `<paragraph>`와 `<list><item>`은 텍스트 블록이 됩니다. HTML 경로처럼 `page=1`로 두고, `ref`에는 절 ID를 넣습니다. 경로 이름은 `SPL`입니다 |
| 1-7 | 상용구·절 규칙 | Highlights, 목차, Recent Major Changes, 환자용 설명서, 사용설명서를 LOINC 코드로 표시합니다. 그러면 지금 청커의 정규식 제외 규칙과 `query.py`의 라벨 절 규칙(적응증 → 1절, 용법 → 2절 …)을 코드로 정확히 맞출 수 있습니다. 예: 적응증 34067-9, 용법·용량 34068-7, 이상반응 34084-4. 코드 목록은 실제 SPL로 확인합니다 ⚠️ |
| 1-8 | 인용 | XML에는 쪽이 없습니다. 인용은 절 번호와 제목(예: "1.2 Psoriatic Arthritis")으로 합니다. HC HTML 문서가 이미 같은 처지이므로 `ra-answer`의 HTML 인용 방식을 따릅니다. 검색 정답 세트에서 라벨 PDF 쪽을 가리키는 묶음은 `eval/retrieval/check_gold.py`로 확인한 뒤 다시 매핑합니다 |

**합격 기준**
- **파싱 비교:** 4개 바이오시밀러와 Stelara의 현행 FDA 라벨에서 SPL 결과와 기존 PDF 결과를 비교합니다. 절 목록이 일치해야 합니다. 표 칸이 다르면 칸별로 확인해서 어느 쪽이 맞는지 기록합니다.
- **검색 평가:** 라벨 문항 재현율이 같거나 오릅니다. 다른 문항은 변화가 없습니다.
- **시간:** FDA 라벨 440쪽의 Docling 처리(쪽당 2~6초)가 XML 파싱(문서당 수 초)으로 바뀝니다.

### 단계 2: EMA 제품정보 정리

| # | 작업 | 우선 | 내용 |
|---|---|---|---|
| 2-1 | Annex 표시 | P1 | 제품정보 PDF는 Annex I(SmPC), II, IIIA(포장 표시), IIIB(포장설명서)를 묶은 문서입니다. `section_path` 맨 앞에 Annex를 넣습니다. 라벨 절 규칙은 기본으로 Annex I을 검색하고, 포장설명서는 환자용 질문일 때만 검색합니다. 881쪽 중 Annex I의 비중을 측정한 뒤, IIIA 처리를 뺄지 정합니다 |
| 2-2 | 수정 추적 DOCX | P2 | 최근 절차에서 바뀐 문장(삽입과 삭제)이 들어 있습니다. "최근 라벨에서 무엇이 바뀌었나"라는 질문의 원천입니다. `w:ins`/`w:del`을 추출해 변경 블록으로 만듭니다. 질문 세트에 해당 문항이 생기면 진행합니다 |
| 2-3 | ePI 감시 | P2 | 제품에 ePI가 생기면 FHIR 경로를 추가합니다. 우스테키누맙은 1차 도입 대상(백신·항암제)이 아니라 늦을 것입니다. 지금은 구현하지 않습니다 |

### 단계 3: HC XML PM 확인

| # | 작업 | 내용 |
|---|---|---|
| 3-1 | 확인 | DPD 제품 페이지에 XML PM 링크가 있는지 봅니다. 특히 2025-07 이후 NOC를 받은 Yesintek(BMAB1200, 2025-10-17)을 확인합니다 ⚠️ |
| 3-2 | 있으면 | XML PM은 SPL 기반이므로 `spl.py`를 재사용합니다. 절 코드 체계는 HC 것이라 매핑표가 필요합니다 |
| 3-3 | 없으면 | PDF를 유지합니다 |

## 5. 하지 않는 것

- Drugs@FDA 라벨 PDF를 적재에서 빼지 않습니다. 판 이력의 원천입니다.
- 라벨 계열에서 바이오시밀러 근거를 추출하지 않습니다. 근거는 심사 계열에 있습니다(2.1절 1번).
- ePI(FHIR) 경로는 지금 구현하지 않습니다.

## 7. 열린 질문

1. **라벨 판 이력을 색인에 넣을지.** 지금은 최신판만 색인합니다. Stelara 적응증 이력은 EMA 변경 평가보고서로 답하고 있습니다(`config/reference_docs.yaml`의 `indication_history`). FDA·HC 쪽 이력 질문이 생기면, Drugs@FDA 판별로 적응증 절만 처리하는 방안을 검토합니다.
2. **유통사별 SetID 중 대표를 무엇으로 할지.** 허가권자 기준(1-2)이 맞지 않는 경우가 있는지 첫 실행에서 확인합니다.
